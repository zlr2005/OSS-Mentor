# 按用户要求放宽候选准入

用户认为上一轮过于保守，要求尽量增加可推荐数据。本轮对原来自动隔离的 4,849 条使用明确的 `expanded-content-v1` 策略；此前 22 条初判汇总/项目背景的记录继续移出独立任务池。原始数据一直保存在库内，本次调整准入而非重新伪造任务。

## 调整内容

- 类型为 `other`：允许进入后续状态检查，保留“类型待确认”提示，不强行改成某个已知类型。
- 范围为 unclear 或 design_pending：改为范围/方案需沟通提示，保留原始低置信度判断。
- 信息待补、讨论等软信号：不再单独阻止候选；历史提交引用和普通认领意向不等同当前占用。
- 明确正在处理的文本、已分配、关联开放 PR、锁定、关闭、明确 blocked/duplicate/invalid/wontfix 等实际阻碍继续拦截。
- 空正文、纯占位模板、缺少最基本描述、非独立任务、缺少技能要求或非法难度值仍不准入。
- 用户语言、难度、技能、系统兼容性限制保持。未知类型可以作为探索候选匹配，但没有类型偏好加分，也不伪装成类型多样性覆盖。

放宽策略只对本批有明确标记的候选生效。默认严格规则保持；普通后台刷新会读取候选的持久化策略并沿用，不会因刷新丢失放宽设置。策略来自本机控制元数据，不读取 Issue 正文里的所谓配置或指令。

## 应用与运行

先对两份业务库备份，并在副本上验证策略标记只改变指定候选的特征元数据；身份、原文、技能要求、核验时间、反馈等其他数据保持一致。标记阶段的推荐池仍为 2,785，没有跳过状态核验。

初始内容门槛分析中，4,763 条可进入状态核验，86 条当时仍缺少最低内容等必要条件。这是内容潜力数，不是新增推荐数。

本轮已启动后台有限队列，对全部 4,849 条重新采集当前详情、仓库状态、完整时间线及引用 PR 状态，不继承旧来源缓存。每批按剩余额度计算预算、最多四路 GET；额度不足等待恢复，读取失败有限重试。新来源仍可能显示关闭、占用或阻塞，只有通过检查的记录才实际回到推荐池。

一个实际运行快照中，264 条已完成状态检查，其中 155 条恢复可推荐，两份业务库可推荐数从 2,785 增至 2,940；该数会继续变化，最新进度见 `data/expanded_admission_20261026_v1/report.md`。

目录中 `manifest.json` 记录策略与代码散列，`preparation_audit.json` 保存应用前的保护性比对，`*.before` 和 `*.staging` 为备份与演练副本，`jobs.json` / `runner_state.json` 为断点与当前运行状态，`evidence/` 保存实际新读取的证据。

新增 14 项策略测试通过，覆盖软条件放宽、未知类型不伪装、模板和非法输入拦截、明确占用、当前开放 PR 优先、过期禁推、偏好不假加分、刷新继承和警示传播；相关特征、匹配、同步、推荐服务和 API 回归通过。API 测试时按进程范围移除了本机继承的 TLS 调试日志环境变量，未更改系统设置；采集进程也不启用该日志。

本轮扩大的是现有规则推荐候选范围，未声称完成 CODER 权重训练或推理。
