# 补充论文阅读与数据集可用性核查

核查日期：2026-10-14。阅读对象：`补充论文/` 中全部 6 篇 PDF，共 76 页。以下区分论文报告的实验结果、公开附件的说明、实际检查到的文件，以及针对 OSS-Mentor 的判断。

## 先看结论

最适合本项目的组合是：**PFIRec 用于个性化排序评估，GFI-Bot/RecGFI 用于新手任务识别，导师数据用于支持信号研究，IssuePilot 用于冷启动画像和导学文档原型。**

这些数据主要记录历史事件，不能直接成为今天仍可领取的任务库存。线上继续使用项目已有的候选采集与 GitHub 状态复核；历史论文数据用于离线实验。6 篇中没有一套数据直接提供“能力增长、适当挑战和连续成长路径”的完整真实标签，成长通道仍需自己的纵向贡献记录与人工评价。

## 1. RecGFI：判断一个任务是否适合项目新手

- 论文：**Recommending Good First Issues in GitHub OSS Projects**，ICSE 2022，13 页。
- 本地原文：[PDF](../补充论文/2022-ICSE-Recommending%20Good%20First%20Issues%20in%20GitHub%20OSS%20Projects.pdf)。重要位置：第 3–5 页为定义、特征和数据构造，第 6 页为实验表，第 10–11 页为局限。

问题：手工标注的 good first issue（GFI）数量少，而且维护者认为容易的任务未必适合新手。因此，不能只复制已有 GFI 标签。

方法：把任务是否被项目新手解决作为监督信号，使用 XGBoost 做二分类。输入包含三个维度：内容（标题、正文、标签、可读性、链接和代码片段等）、背景（报告者经验、项目和所有者特征）、动态（评论、事件和参与者）。新人是相对于一个项目定义的，可以已经在别的项目有丰富经验；原论文按在当前项目中贡献的 commit 数是否不超过阈值 k 来划分。

论文构建了 100 个 GitHub 项目中 53,510 个已解决 Issue 的数据。每个 Issue 恢复两个历史时点：创建时、有人开始处理前；第二个时点通常取第一次关联 PR/分配事件前，没有相应事件时取关闭前。这样避免把未来的解决结果混进特征。论文最高 AUC 为创建时 0.801、第二时点 0.853；这是排序区分能力，不是 85.3% 的任务完成率。对真实开放任务的试验中，33 个收到维护者回应的推荐有 16 个被确认是 GFI，论文记录了其中及其他推荐中的 5 个新手解决案例。

意义：为 OSS-Mentor 的新手通道提供一个可复现、计算成本较低的经典基线。也支持现有“任务清晰度、项目支持、新人历史成功信号”的特征设计。

局限：预测的是一般项目新手适合度，不是某个具体人的适合度；经验丰富者解决过的任务也可能适合新手，因此负样本不等于绝对不适合。问答、重复报告等非开发任务还要先过滤。

公开资源：

- [Zenodo 复现包](https://zenodo.org/records/5881117)：页面和元数据可访问。`issuedata.zip` 172,259,091 字节（约 172.3 MB）；`RecGFI.zip` 约 8.6 MB。其余主要是分卷虚拟机，整页约 15.1 GB，不必为了获取数据而下载虚拟机。
- [作者代码](https://github.com/mcxwx123/RecGFI)：可访问，仓库标记 MIT；Zenodo 元数据也标记 MIT。
- 本次没有下载完整训练数据，也没有运行复现实验。

## 2. GFI-Bot：把 RecGFI 变成持续运行的系统

- 论文：**GFI-Bot: Automated Good First Issue Recommendation on GitHub**，FSE 2022 工具论文，5 页。
- 本地原文：[PDF](../补充论文/2022-FSE-Automated%20Good%20First%20Issue%20Recommendation%20on%20GitHub.pdf)。重要位置：第 2–3 页的数据、架构和实验。

问题：RecGFI 原始数据依赖 GHTorrent，历史镜像有缺漏，且难以持续更新；研究算法也需要真正接入维护者和新手的工作流程。

方法：沿用 RecGFI/XGBoost，将 GitHub REST/GraphQL 采集、增量更新、模型训练、网页探索和 GitHub App 组合起来。维护者可以配置推荐后添加标签或评论；新手可以按语言等浏览候选。它主要是通用 GFI 识别系统，网页筛选不等于完整的个性化学习排序。

论文统计：100 个项目中获取 907,869 个 Issue，其中 159,919 个可追溯到解决 commit/PR 的 Issue 用于训练，最高 AUC 0.8302。这个 159,919 是论文写作时的已解决 Issue 数，不能直接当成当前下载包的文档数；一个 Issue 还可能有多个历史时点记录。

意义：它提供了比 RecGFI 原版更方便重新利用的数据结构，尤其是“谁通过哪个 PR/commit 解决了哪个 Issue”，有助于用户历史贡献画像、个性化匹配与后续留存研究。工程上值得借鉴增量采集和明确的训练/开放任务分离。

公开资源：

- 论文链接：[概念 DOI](https://doi.org/10.5281/zenodo.6665931)。核查时它对应 [2022-07-15 发布的 0.0.3 版本](https://zenodo.org/records/6837711)，`dump.zip` 2,463,994,466 字节（约 2.46 GB，页面四舍五入显示 2.5 GB）。复现实验应固定版本链接。
- 格式为 MongoDB dump，官方说明要求用 `mongorestore --gzip` 恢复。
- `gfibot.dataset`：某个历史时点的任务特征；`resolver_commit_num` 表示解决者解决任务前在该项目的 commit 数，排除本次解决任务所需提交。值为 0 表示对这个项目完全没有提交历史。
- `gfibot.resolved_issue`：解决者和对应 commit/PR 信息。
- 数据 Zenodo 元数据标记 CC BY 4.0；[代码仓库](https://github.com/osslab-pku/gfi-bot)采用 GPL v3。数据和代码许可应分别处理。
- 页面/API 可访问；本次没有下载和恢复完整数据库。小范围附件探测被服务器以 403 拦截，不能据此断言正常浏览器完整下载失效。

## 3. PFIRec：同一个任务对不同开发者是否合适

- 论文：**Personalized First Issue Recommender for Newcomers in Open Source Projects**，ASE 2023，13 页。
- 本地原文：[PDF](../补充论文/2023-ASE-Personalized_First_Issue_Recommender_for_Newcomers_in_Open_Source_Projects.pdf)。重要位置：第 3–6 页的实证研究，第 7–10 页的排序和评估。

问题：一般的 GFI 推荐把新手视为同一种人，但不同人的技术、领域、经验和当前活跃程度差异很大，统一推荐会产生错配。

方法：先分析 37 位在多个项目完成首次任务的开发者及 123 个首次解决 Issue，发现同一个人的首次任务常在类型、语言、项目领域上保持一致。随后用个人历史行为建立四类特征：专业/领域偏好、总体开源经验、近期活跃度、文本情绪；与任务内容和背景特征一起输入 LambdaMART 排序。文本相似度采用 SimCSE 等表示。情绪特征是研究中的关联信号，不能把它解释为可靠的个人能力或性格评分。

数据：从 GFI-Bot 和 GitHub GraphQL 补充用户历史，得到 100 个项目的 68,858 个候选 Issue、11,615 个候选列表。每个列表对应一次首次解决任务的场景，实际解决的 Issue 标为 1，其他当时开放的候选标为 0；列表的候选数中位数为 32。11,615 是场景/列表数，不宜直接当成不同开发者人数。

结果：论文报告中位 R@1 从 GFI-Bot 的 0.07 增到 0.15，R@10 从 0.52 增到 0.61；FirstHit 中位排名为 7，相比基线的 10，得到“潜在无效尝试从 9 次减少到 6 次”的离线估计。这些是历史排序指标，不能宣称真实用户贡献成功率翻倍，或实际失败次数已经减少三分之一。

意义：6 篇里最直接对应 OSS-Mentor 的个性化推荐核心，可以比较规则排序、文本相似度排序和 LambdaMART 等方法，并采用 Recall@K、FirstHit、NDCG@K 等指标（原论文主要用前两种）。

局限：项目新手可能是开源老手；无 GitHub 历史者的个性化信号很少。未被某人选择的候选不一定是不合适的任务。它也不提供连续成长路径的评价标签。

公开资源：

- [Zenodo](https://zenodo.org/records/7915841)：`ReplicationPackage.zip` 731,517,850 字节（约 731.5 MB），元数据标记 CC BY 4.0。
- [作者代码](https://github.com/mcxwx123/PFIRec)：代码和 README 已访问，`model.py` 已只读检查。
- `data/dataset_{bertmodel}_{num}.pkl`：开发者—候选任务特征，四种文本表示、20 个时间折；实际代码使用 `simcse`、`codebert`、`BERTOverflow`、`roberta` 等名称。
- `training_set_recgfi_simcse_{num}.pkl`：GFI-Bot 基线训练数据。
- `newcomerdata.json`、`processeddata.pkl`、`isstexts.json`：首次任务/部分用户信息、37 人实证研究特征、任务文本。
- `PFIs.csv`：123 个手工标注样本；`empirical.py`、`model.py`：研究及模型复现脚本。
- 代码确认排序使用 `issgroupid` 分组、`match` 作监督标签、LightGBM `LGBMRanker`。这是从作者代码确认的字段，不代表已打开每个 pkl 核查完整 schema。
- 作者建议至少 1 CPU、8 GB 内存和 100 GB 可用空间，压缩包大小不代表解压和实验资源需求。
- 本次未下载完整包、未验证各时间折实际日期方向、未运行模型；使用前仍要检查训练时间严格早于验证/测试时间。小范围下载探测遭遇 403。

## 4. 导师研究：找到任务之后，还需要哪些帮助

- 论文：**Is It Enough to Recommend Tasks to Newcomers? Understanding Mentoring on Good First Issues**，ICSE 2023，12 页。
- 本地原文：[PDF](../补充论文/2023-ICSE-Is_It_Enough_to_Recommend_Tasks_to_Newcomers_Understanding_Mentoring_on_Good_First_Issues.pdf)。重要位置：第 3 页的数据口径，第 7 页的支持类型，第 9–11 页的统计结果、局限和数据链接。

问题：仅仅推荐一个看起来适合的 Issue，并不保证新手能理解项目、配置环境、编写测试并提交 PR，因此需要研究日常导师帮助。

方法与数据：基于 GHTorrent 2021-03-06 镜像，初选 964 个 GFI 多的仓库；正文在过滤进行中任务后，最终写明 947 个仓库、48,402 个已关闭 GFI、286,371 条评论，其中 176,674 条 Issue 评论、109,697 条 PR/commit 评论。摘要沿用 964 仓库口径，实际分析规模建议引用正文的过滤后口径。

专家按评论前一年项目贡献 commit 数前 20% 定义；新手为项目中少于 3 个 commit 的开发者。研究结合统计、协作网络、43 个讨论充分的 GFI 的主题分析和问卷，归纳集中式、分散式、协作式、分布式四类导师网络，以及 14 种新手困难、18 种导师支持内容。

主要发现：约 70% GFI 有专家参与；在定义的专家回复场景中，半数的首次专家响应在 8.5 小时内。支持内容包括澄清目标、指出目标文件、提供示例、环境和测试指导、PR 规范、反馈与鼓励。专家参与和首次贡献成功正相关，而与后续留存在统计模型中负相关；作者明确指出这是相关性，不能推出“指导导致流失”。留存模型解释能力较弱，开发者自身能力和意愿等因素仍然重要。

意义：为 OSS-Mentor 增加“可获得的支持”和“完成任务所需导学材料”提供依据。推荐理由可以包括维护者支持、环境/测试说明；选定任务后输出上手步骤和验证清单。历史响应速度只是辅助信号，不能保证下一次响应。

公开资源：

- [Figshare 分享入口](https://figshare.com/s/addd697d581c82f96f9a)：可访问，显示 `GFI_mentor_data`、461.04 MB、CC BY 4.0。
- 页面标记 privately shared，但持论文中的分享链接即可看到条目和下载入口，不等于已经撤回或必须申请授权。
- 页面显示附件下载入口；本次工具获取附件遭遇站点响应限制，未成功下载，尚未核查压缩包内文件结构和字段。论文称公开数据与脚本，不能把这一声明等同于逐文件检查。
- 在取得附件并确认评论、时间、角色等字段后，可用于导师支持分析、支持内容分类和历史案例整理；若用作 AI 导学评价，需要额外标注输出质量。

## 5. CTCK：使用知识图谱缓解交互稀疏和长尾问题

- 论文：**Cross-space topological contrastive learning for knowledge graph-aware issue recommendation**，Knowledge and Information Systems 2025，28 页。
- 本地原文：[PDF](../补充论文/2025-KAIS-Cross-space%20topological%20contrastive%20learning%20for%20knowledge%20graph-aware%20issue%20recommendation.pdf)。重要位置：第 7–12 页的方法，第 13–17 页的主数据/评估，第 21–23 页的通用数据和可用性声明。

问题：用户与任务的交互很稀疏，热门任务和长尾任务差异大；单一空间表示难以同时捕捉一般关联和层级关系。

方法：构建包含开发者、Issue、标签、PR 等实体的 ISSUEKG，把协同过滤信号和知识图谱分别在欧氏空间、双曲空间聚合；再用空间内及跨空间对比学习减少噪声，并联合 BPR 推荐损失训练。直观上，一种表示学习常见关联，另一种表示学习层级，训练让两种视角彼此协调。

主实验来自 freeCodeCamp，过滤后有 2,432 个开发者、13,923 个 Issue、32,108 次交互；知识图谱含 25,369 个实体、12 种关系、23,918 条三元组。模型 AUC 0.7716、F1 0.7260，优于比较基线。论文还在 Last.FM 和 BookCrossing 上测试通用推荐能力。

对项目的意义：未来可以把用户—任务—技能—项目—文件连接成图，研究长尾推荐。但它的监督目标是用户与任务交互/采用关系，不是已核实的首次成功贡献，更不是能力增长。论文还过滤掉交互少于 2 次的开发者/任务，因此不能仅凭这些实验认定零历史用户冷启动已被解决。

公开资源与限制：

- **ISSUEKG/freeCodeCamp 实验数据没有在本地论文中给出公开下载地址，本次也未找到可确认属于作者的复现仓库。** 第 23 页的 Data availability 声明甚至写“本研究未生成或分析数据”，Code availability 为“Not applicable”，与实验正文的采集描述存在不一致。因此不能把 ISSUEKG 当成已经可下载的数据集；可以列为需向作者询问的资源。
- [Last.FM 原始数据入口](https://grouplens.org/datasets/hetrec-2011/)可访问，有 README 和压缩包链接。适合验证通用推荐算法，不能直接训练开源贡献适合度。论文处理后的 KG/样本规模不等于原始 Last.FM 下载规模。
- BookCrossing 在论文中的 Freiburg 地址本次未成功访问；[GroupLens 官方介绍](https://grouplens.org/datasets/book-crossing/)仍可访问并指向原站。不能说原始附件已确认可下载。它也是图书评分数据，只适合辅助算法验证。
- 即使重新采集 freeCodeCamp，也不是论文原数据的完全复现：时间范围、实体对齐、关系生成和交互判定都需重新定义。

## 6. IssuePilot：让没有贡献历史的人也能获得推荐与导学

- 论文：**IssuePilot: An Agentic Framework for Personalized Issue Recommendation and Onboarding in Open-Source Projects**，MSR 2026，5 页。
- 本地原文：[PDF](../补充论文/2026-MSR-An%20Agentic%20Framework%20for%20Personalized%20Issue.pdf)。重要位置：第 2–3 页的流程，第 4 页的评价和局限，第 5 页的资源链接。

问题：PFIRec 等依赖已有贡献历史，完全没有 GitHub 历史的人很难建立画像；选出任务后仍需要理解项目和知道怎样开始。

方法：从简历抽取技能，通过 3 个问题获取当前兴趣，优先匹配兴趣、其次匹配已有技能。采集仓库目录、依赖和架构信息，再针对选择的 Issue 生成包含项目概述、代码理解、实现与测试策略、资源和下一步的导学文档。论文使用多个职责明确的 Agent 和 Gemini 2.0 Flash；仓库缓存按周更新。论文描述的任务采集为近期 100 个开放 Issue，并筛掉已经有相关 PR 的任务。

结果：15 人使用后的 UTAUT2 等主观问卷，论文报告约 80% 接受、约 86.6% 愿意继续使用和推荐给他人。样本很小，主要是可用性/有用性感知，不是大规模推荐准确率和真实完成率对照实验。论文实现阶段的仓库分析主要支持 JavaScript、Python，大仓库受上下文和计算资源限制。

意义：直接支持 OSS-Mentor 的零历史用户画像、当前成长意图和任务导学设计。可以借鉴“已有技能”和“想学习什么”分开建模，以及推荐后给出具体文件、环境、测试入口。

实际检查到的资源：

- [Zenodo 附件](https://zenodo.org/records/18363387)：`issue-pilot.zip` 1,245,414 字节（约 1.25 MB），元数据标记 CC BY 4.0。本次已经下载，MD5 与官方 `6e1bbbe42b2ae66582f00c111902c6a1` 一致；只读检查，未执行附件代码。
- 包含代码、README、`repo_analysis_output/<组织>/<仓库>/issues.json` 和 `metadata.json`。
- 实际统计 **21 个仓库、1,127 条 Issue 缓存**，采集时间为 **2025-10-31 和 2025-11-07**。这里的条数来自附件，不是论文声称的训练集规模。
- Issue 字段包括 `number/title/body/state/created_at/updated_at/html_url/labels/assignees`；元数据包括 `repository_info/directory_structure/dependency_graph/architecture_analysis/extracted_at/summary/ai_summary` 等。
- 它提供历史任务内容和代码结构上下文，但**没有可直接训练个性化排序的开发者—任务成功标签**。历史 `state=open` 不能当成 2026-10-14 的实时可领取状态；`ai_summary` 也是机器生成内容，需对照代码核实。
- 附件 README 声明 MIT，而 Zenodo 元数据声明 CC BY 4.0。若复制代码或再分发附件，应核对具体文件许可，不能统一假定一种许可。
- [公开匿名问卷](https://docs.google.com/spreadsheets/d/17XHT9uE3XMMXGEFy90U7rRrlwH1SDMo3y8o-Q6Sc5uk/edit)通过 CSV 导出成功获取，确认 **15 份匿名回答**。可借鉴评价问题，但不是排序训练数据。
- [在线演示](https://huggingface.co/spaces/b30wulffz/issue-pilot)为论文提供地址；本次工具未成功访问，未验证当前运行状态或向演示上传个人简历。

## 接入 OSS-Mentor 时的具体建议

1. **先把离线评估做实。** 若研究问题是个性化排序，优先 PFIRec；若想快速建立新手任务分类基线，先 RecGFI；若需要解决者和 PR 的关联分析，优先 GFI-Bot。论文基准与项目当前自建任务适合度标注集分别报告。
2. **历史训练与当前任务库存分开。** 历史数据里的任务大多已完成，缓存中开放任务也会过期。线上推荐仍需 GitHub 复核是否开放、是否分配、是否已有处理 PR、仓库是否活跃等。
3. **避免结果泄漏。** `resolver_commit_num`、解决者身份、最终关联 PR/commit、关闭后的评论等用于标签或回溯审计，不能作为推荐时可见的特征。GFI-Bot 一个 Issue 的不同时间快照不能随机拆到训练和测试两边；PFIRec 以场景为组，检查时间顺序，并处理重复 Issue 跨场景的影响。
4. **正确理解负样本。** 没被某人选择、没被新手解决、没发生交互，分别是不同监督定义，都不能无条件解释为“这个任务不可完成或不合适”。
5. **单独测零历史用户。** 不能拿有大量跨项目历史的项目新手评估结果代替零开源经验用户的效果。对零历史用户，结合自报技能、课程/个人项目证据、可投入时间和兴趣；参考 IssuePilot 的交互方式。
6. **成长通道需要新数据。** 增加贡献前后技能证据、任务难度、人工判断的成长空间、实施时长、完成/放弃原因、复盘和后续贡献轨迹。历史首次任务排序数据可以做基础实验，不能证明成长路径有效。
7. **导师数据用于设计和验证支持。** 优先整理“任务目标—相关文件—环境搭建—最小修改—测试—PR 提交”导学结构，并测量事实正确性、步骤可执行性、是否减少启动时间；不能仅以主观满意度替代贡献结果。
8. **不要简单把三套推荐数据拼接当新数据。** RecGFI、GFI-Bot、PFIRec 同属研究脉络，项目集合高度相关，PFIRec 明确基于 GFI-Bot。合并前按仓库和 Issue 编号去重、保留采集时间和监督定义，防止重复样本导致虚高评估。
