OSS-Mentor 难度人工标注规范 v0.1

1. 目的

本规范用于建立 B3 难度校准集。标注结果用于评估当前难度估计与人工判断的偏差，不直接等同于最终实现公式。

标注对象为固定 36 条 eligible Issue。每条任务独立标注：

code_difficulty

setup_difficulty

project_context_difficulty

collaboration_difficulty

effort_bucket

annotation_confidence

rationale

evidence

标注时不得查看 difficulty_calibration_current_predictions_v0.1.json。必须先完成并冻结人工标注，再进行误差比较。

2. 基本原则

只根据任务内容判断：使用标题、标签、正文摘录和评论数，不使用当前模型预测。

四维独立标注：一个维度高，不代表其他维度必须高。

Effort 独立判断：不得把四维简单相加后机械生成 effort_bucket。

区分任务难度与 Issue 热度：评论多不自动等于协作难度高。

区分出现关键词与实际要求：正文提到 Linux、Docker、backend，不自动代表必须搭建对应环境。

信息不足时保守记录：不要猜测未提供的实现范围；降低 annotation_confidence，并在 rationale 中说明缺失信息。

不根据 newcomer 标签降难度：good first issue 只能作为维护者意图证据，不能覆盖任务本身的技术复杂度。

不根据 performance 标签统一判高难度：benchmark、参数调整、内存泄漏和执行引擎重构应分别判断。

3. Code difficulty

0：不需要代码修改

典型情况：

纯文档、措辞、示例文本、链接或内容调整；

不需要修改程序逻辑；

仅更新说明文件，且无需验证复杂行为。

不应仅因任务类型是 documentation 就自动标 0。若文档任务要求修改文档生成器、示例代码或自动化逻辑，应按实际代码工作标注。

1：局部、明确、低风险修改

典型情况：

修改单个函数、条件、常量或配置；

增加简单测试或修复明确局部 Bug；

影响范围清晰，回归风险较低；

不需要设计新的抽象或跨模块联动。

2：非平凡逻辑或模块内联动

典型情况：

修改多个函数或同一子系统中的多个位置；

新增一项完整功能或非平凡算法；

需要处理边界、兼容性或多种执行路径；

测试、实现、配置需要协同修改；

有中等回归风险。

3：架构、核心协议或高风险实现

典型情况：

并发、编译器、运行时、分布式协议、核心调度或存储机制；

跨多个核心模块或需要重构全局不变量；

高性能底层路径、内存模型或兼容性边界；

大范围、高风险、难以局部验证的修改。

4. Setup difficulty

0：无需特殊运行环境

纯内容修改；

可以不运行项目完成；

不需要安装仓库依赖或外部服务。

1：标准仓库环境

按项目常规说明安装依赖即可；

普通单机测试；

不要求特定操作系统、服务或工具链。

2：特定环境或复杂复现

需要特定操作系统、数据库、浏览器、服务、编译器或工具链；

需要搭建 CI 类环境、容器、特定 backend 或较复杂复现步骤；

单一特殊平台或中等成本基础设施即可完成。

3：多平台或高成本基础设施

多操作系统验证；

native、GPU、分布式集群、多节点服务或高成本数据环境；

复杂交叉编译、系统级依赖或难以稳定复现的基础设施。

注意：正文中“提到”某个平台不等于“完成任务必须使用”该平台。必须从任务目标和复现要求判断。

5. Project context difficulty

0：几乎不需要项目知识

完全独立的文本或资源修改；

任务目标和修改位置直接给出；

不需要理解项目模块关系。

1：理解局部模块即可

修改范围在一个模块或组件中；

需要阅读局部调用关系；

不涉及公共契约或跨模块生命周期。

2：跨模块、公共 API 或生命周期知识

需要理解多个模块如何交互；

涉及公共 API、序列化格式、扩展机制、生命周期或兼容性；

修改可能影响多类调用者。

3：核心架构或全局设计知识

涉及核心架构、全局不变量、协议、调度、编译管线或历史设计约束；

需要理解系统级数据流和多个核心子系统；

局部修改无法安全完成。

注意：标签中出现 api、core 或 architecture 只能作为线索，不能单独决定等级。

6. Collaboration difficulty

0：范围明确，无需额外协调

需求清晰；

接受标准明确；

没有明显设计分歧；

正常代码审查即可。

1：少量澄清或普通 Review

可能需要确认一个实现细节；

方案基本明确；

仅需常规维护者反馈。

2：存在设计选择或多方协调

有多个可行方案；

涉及公共接口或多个维护者；

Issue 中仍有关键问题待定；

需要在实现前确认方向。

3：RFC、多团队决策或高不确定性

明显争议、长期未决设计、RFC 或 roadmap；

涉及多个团队或仓库；

需求本身尚未收敛；

即使技术实现可行，也不能由单个贡献者独立决定。

注意：评论数量只是参考。大量评论可能来自 Issue 年龄、机器人或用户重复反馈。

7. Effort bucket

Effort 表示一名具备所需技能、熟悉基础贡献流程的开发者完成该任务所需的有效工作量。它必须独立判断，不由四维总和直接生成。

under_2h：非常局部，定位清晰，修改和验证可在约两小时内完成；

half_day：约半天，需要常规实现、测试或文档验证；

one_day：约一个完整工作日，需要非平凡实现、复现或多处修改；

multi_day：需要多日设计、实现、环境搭建、跨模块验证或协调。

若 Issue 是 roadmap、umbrella、纯讨论或不可直接领取的聚合任务，不能仅因内容广泛就标为 multi_day。应在 rationale 中说明“不是单一可执行任务”，并使用低置信度；后续误差分析应单独处理这类样本。

8. Annotation confidence

high：标题和正文充分，范围与验收标准清晰；

medium：能够合理判断，但仍缺少部分实现或环境信息；

low：正文缺失、任务是讨论/roadmap，或范围高度不确定。

低置信度不代表任务简单或困难，只代表标注依据不足。

9. Rationale 与 Evidence

rationale

用 1～4 句话解释整体判断，至少说明：

主要修改范围；

特殊环境要求；

是否需要跨模块知识；

是否存在协调或不确定性。

不要写“因为当前模型是 2”之类内容。

evidence

evidence 是字符串数组，只记录能支持判断的可核对信息，例如：

[
  "标题要求修改单个公开 API 的返回行为",
  "正文给出明确复现步骤和预期结果",
  "需要在 Linux 与 Windows 上验证",
  "Issue 中存在两个尚未决定的设计方案"
]

不得复制大段正文、日志或代码。

10. 标注流程

打开 data/annotations/difficulty_calibration_v0.1.json；

只查看每条记录的 annotation_input；

独立填写 human_annotation；

检查所有字段均已填写；

由第二名成员独立复核至少 12 条，优先选择：

4 条 performance + newcomer；

2 条正文缺失；

2 条 documentation；

2 条 setup 正文触发；

2 条 testing/build-tooling；

冻结人工文件；

再打开 difficulty_calibration_current_predictions_v0.1.json 做误差分析。

11. JSON 填写约束

四个难度字段必须是整数 0、1、2 或 3；

effort 必须是四个枚举之一；

confidence 必须是 low、medium 或 high；

rationale 必须是非空字符串；

evidence 必须是至少一个非空字符串组成的数组；

不修改 annotation_input；

不向人工文件复制 current_prediction。

12. 本阶段边界

该校准集用于发现公式偏差。本阶段不：

修改 task_features.py；

修改 effort 阈值；

修改任务类型或技能规则；

修改 matching；

写入 SQLite；

将 36 条人工结果直接视为通用最终公式。
