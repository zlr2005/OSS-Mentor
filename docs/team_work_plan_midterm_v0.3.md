# OSS-Mentor 中期答辩：四人并行开发与交付规范 v0.3

制定日期：2026-10-15。适用对象：成员 A、B、C、D。排期暂按四周，以实际中期日期调整。

本文是本轮开发的执行依据。它规定任务、文件归属、交付物、共享接口、依赖、集成顺序和交付消息模板。文中新增目录、命令、接口和模型均为待实现的约定，不代表仓库已经具备这些能力。

使用顺序：四人共同看第 1—7 节；A/B/C/D 分别执行第 8/9/10/11 节；按第 12—14 节安排交接和验收；交付消息直接复制文末第 16 节模板。

## 1. 本轮目标与边界

### 1.1 五个任务

| 编号 | 中期任务 | 主负责人 | 配合人 |
|---|---|---|---|
| T1 | 建立独立数据库，导入论文数据，扩充历史训练数据和当前可推荐库存，预留老师数据库接入 | A | D 负责公共数据库接入；C 定义模型所需数据 |
| T2 | 首页直接展示推荐，推荐过程独立展示，个人画像移入个人信息界面 | D | B 提供画像业务；C 提供推荐业务；A 提供任务与项目详情 |
| T3 | 复现原版 CODER 作为 baseline，并在其基础上优化、对比和消融 | C | A 提供数据；B 提供增强画像；D 接入模型服务 |
| T4 | 增加能力与兴趣问题，将回答、自评和贡献证据融合为可编辑画像 | B | D 制作页面并接 API；C 消费模型特征 |
| T5 | 从实际 GitHub 贡献、文件修改和代码中提取更丰富的画像与行为证据 | B 负责画像结果 | A 负责采集代码与行为；C 负责 CodeBERT 编码；D 负责触发与状态展示 |

### 1.2 算法口径必须统一

1. **主 baseline 是原版 CODER，不是现有规则排序。** CodeBERT 本来就在 CODER 内，不能把“加上 CodeBERT”当成我们的创新。
2. 原版 baseline 的目标是复现论文的代码语义、代码与贡献者融合、层级结构、用户—文件/项目行为、预测与训练目标。
3. 原版 CODER 推荐代码文件。本项目增加统一的文件到 Issue/项目映射层，并让原版和优化版共用。文件推荐与 Issue 推荐指标分别报告。
4. 优化模块先做“增强画像”，再做“近期行为与当前意图”。仅把原公式换名、调展示分数、改变候选过滤，不算模型优化。
5. 原版训练代码或处理后数据不完整时，按论文补齐并记录复现差异。缺少关键模块的版本标记为 `partial`，不能通过“原版复现完成”验收。
6. 现有规则引擎作为兼容与诊断工具保留；如使用，必须明确显示 `rule_legacy`，不能冒充 CODER。

### 1.3 与旧文档的关系

本轮新目标取代旧计划中的“不接入复杂机器学习”“不训练 CodeBERT/GNN”等阶段性限制。旧文件中仍适用的身份鉴权、存储接口、数据追溯和测试约定继续保留；冲突时以本文为准。

本轮所有网页文件归 D，覆盖旧版中 B 编辑画像页面、C 编辑推荐页面的安排。本文不要求重写现有系统，也不要求先完成 PostgreSQL 迁移才能进行算法实验。

### 1.4 本轮不自动执行的产品行为

- 推荐参与入口，不自动领取 Issue、发表评论、发起 PR 或向维护者申请协作者身份。
- 协作者资格由维护者决定，不能作为系统保证的结果。
- 不将大型代码仓库、数据库、模型权重、密码或 token 提交到 Git。
- 不把少量点击、满意度或手工画像变动直接解释为真实能力提升。

## 2. 四个人如何从第一天并行

### 2.1 启动检查

1. 将各自已有未提交工作保存到各自分支；不覆盖、重置或清理其他人的工作。
2. 确定共同起点的提交 SHA，四人记录相同的 `base_commit`。本文不预设当前 `main` 等同于每个人的本地修改。
3. 使用各自独立 checkout/worktree 或各自电脑，禁止四人共用一个正在修改的工作目录、工作数据库或训练输出目录。
4. 分支名称由各成员自行决定，不统一规定名称或前缀；交付时注明实际分支名。集成负责人为 D，集成分支名称也由 D 自行决定。
5. 每个 PR 都写明负责人、任务编号、依赖 PR、交付物位置和验证结果。不开启超出本人范围的顺手重构。

### 2.2 S0：第一天的接口冻结，不让其他人等待

D 在第一天完成小型公共契约 PR：新增共享数据类型、最小接口定义、版本字段和固定错误格式，不等待完整业务实现。

与此同时：

- A 按第 7 节 JSON 格式准备样例、编写导入和清洗逻辑；
- B 按固定输入输出准备问题、画像融合与单元测试；
- C 审计 CODER 复现条件、建立独立训练目录和最小模型样例；
- D 用明确标记的 fixture 开发页面和网关。

S0 未合并前，业务模块通过参数、字典和本地 mock 工作；不复制一套公共类型到自己的模块。S0 合并后各分支同步该提交并运行契约测试。

### 2.3 日常同步与共享文件请求

- 每个工作日结束发送第 16 节进度模板，重点报依赖、产物和阻塞。
- 需要其他人改文件时，先发第 16 节“接口/共享文件变更请求”，由文件所有者修改。
- 对接口的确认是团队技术协作，不意味着每个普通实现步骤都需要额外审批；已约定范围内自行推进。
- 一个共享文件同时只对应一个在合并中的 PR。D 将 API、契约、迁移登记和依赖锁文件等公共改动排队。
- 使用真实接口联调时写明对方提交 SHA；“我本地可以”不等于集成成功。

## 4. 三个容易重叠的责任边界

### 4.1 A 采集，B 解释证据，C 编码与建模

| 工作 | 负责人 | 输出给谁 |
|---|---|---|
| 获取仓库、PR、commit、修改路径、代码快照和项目文档 | A | B/C |
| 将 Git 作者与 GitHub 身份关联，保留未确认身份 | A | B/C |
| 判断一条记录能支持哪项技能/经历，生成画像建议 | B | C/D |

| 图构建、训练、打分、时间建模、实验与消融 | C | D |
| 登录触发、后台作业状态、API 序列化、页面 | D | 用户 |

CodeBERT 只实现一套，归 C。B 不再独立加载另一套模型。C 提供离线编码接口和缓存产物；B 可先消费固定向量/语义特征 fixture，联调后消费同版产物。问答提交和普通推荐请求不即时扫描全仓或重新训练模型。

`services/github_profile_source.py` 由 B 保留为用户导入编排入口，调用 A 的采集能力，不重复实现第二套 commit/PR/文件网络采集器。

### 4.2 A 负责数据正确，C 负责实验正确

A 输出标准化记录、时间戳、关联关系、质量统计和来源；C 在这些记录上建立节点索引、训练图、负采样和实验划分。**同一正式对比中所有变体共用 C 冻结的划分与候选。** A 不为每个模型单独生成一套有差异的测试数据。

### 4.3 B/C 给出业务结果，D 负责展示

B 交付问卷内容、状态、画像预览和错误；C 交付推荐、模型版本、解释证据与错误。D 不在 JS 中重算画像或推荐分数。B/C 不为完成页面联调而修改 `web/`。

## 5. 数据库、迁移和大型产物约定

### 5.1 首先建立独立数据库

- 本轮默认新数据库路径：`data/midterm/db/oss_mentor_midterm.sqlite3`，不得覆盖既有 `data/oss_mentor.sqlite3`。
- D 统一配置数据库路径、连接创建、事务和迁移执行；A/B/C 通过存储接口写入各自业务数据。
- SQLite 是本轮首先完成的运行方式。已有 PostgreSQL 文档/迁移不自动等于全功能适配完成；若切换，由 D 提供同契约验证，不让算法开发等待迁移。
- 老师的 ClickHouse 是后续数据源。老师库仍不可访问时 A 交付适配器接口和 mock 测试，不写“已同步老师真实数据”。
- 训练进程消费冻结导出文件，网页读取稳定快照；禁止在同一活动 SQLite 文件上四人并发写入或一边训练一边改实验输入。

### 5.2 本轮 SQLite 迁移编号预留

制定本文时，仓库已有 `001` 至 `010`，另有 `009a_profile_user_identity.sql`。旧文件不修改，不重排。

| 编号 | 作者 | 拟议内容 |
|---|---|---|
| `011_midterm_datasets.sql` | A | 来源、标准化实体、贡献/文件关联、代码快照索引、导入批次 |
| `012_midterm_profile_assessment.sql` | B | 问卷版本、回答、证据、画像预览和确认记录 |
| `013_midterm_model_runs.sql` | C | 数据/模型版本、训练与推理产物登记、实验结果索引 |
| `014_midterm_runtime_state.sql` | D，确有需要才创建 | 平台后台作业/模型运行状态等公共扩展 |

A/B/C 分别编写自己的 SQLite 增量迁移及模块测试。D 登记并按顺序集成，测试空库、旧库升级和重复执行行为。编号如已被其他已合并工作占用，由 D 统一重新登记，其他成员不得自行抢号。

本轮已有表的迁移只增不删；需要重建训练表时使用新版本表或新库，不能删除用户画像和反馈。新迁移须明确唯一键、索引和外键删除行为。PostgreSQL 增量由 D 在确定支持后统一追加，不改写已执行的初始迁移。

### 5.3 目录与共享方式

```text
data/midterm/
  db/                         # 本地独立数据库；D 管理运行配置
  sources/<source>/<version>/ # 原始论文附件/来源清单；A
  normalized/<version>/       # 标准化数据与 manifest；A
  code/<snapshot_version>/    # 固定 SHA 的代码/结构或可重新获取索引；A
  profiles/<version>/         # 脱敏画像特征导出与 manifest；B
  embeddings/<version>/       # CodeBERT 缓存与行映射；C
  graphs/<dataset_version>/   # 图、节点映射、时间划分与候选；C
  models/<model_version>/     # 权重、配置、环境信息、校验和；C
  runs/<run_id>/              # 预测、指标、耗时和运行日志；C
  validation/<owner>/         # A/B/D 的机器可读验证记录
```

以上大型目录不提交 Git。A/B/C 交付时附团队可访问的产物位置、版本、大小、SHA-256、获取/生成命令；“文件在我电脑上”不算可交付。D 调整 `.gitignore` 时只增加必要的精确规则。

Git 中只保存实现代码、配置模板、小型合成或许可允许的脱敏 fixture、manifest 模式和精简结果摘要。不因每次执行新建一份报告；阶段说明集中在对应 PR、固定产物 manifest 和本轮交付消息里。

## 6. 数据规模与质量要求

下表为建设目标，验收须填写实测值，不能作为已完成量宣传。

| 对象 | 首次闭环 | 扩充目标 | 判断依据 |
|---|---|---|---|
| 历史 Issue | 小样本可关联到解决者/PR | 至少 5 万条标准化历史 Issue | 去重后计数，区分来源和缺失字段 |
| CODER 训练仓库 | 小图、少量仓库可训练 | 先 10—20 仓库，再根据资源扩展 | 有代码结构和用户—文件交互，不只数仓库名 |
| 用户—文件交互 | 完整作者/文件/时间链路 | 争取 10 万级有效交互 | 清洗、身份关联和时间过滤后的边数 |
| 在线 Issue | 可验证的真实候选 | 争取至少 500 条可推荐任务 | 状态已复核，并报告新手/进阶、语言和类型分布 |
| 人工 Issue 评价 | 固定画像—任务样本可评审 | 建议至少 200 对，含双人复标子集 | 评价单位是用户—任务对，不能只给任务打通用分 |

A 负责导入计数与分布；C 负责有效训练/测试计数；B 和 C 共同定义人工适合度标注指南，由至少两名团队成员进行评价，D 可参与复标。

数据使用规则：

- GFI-Bot/RecGFI/PFIRec 来源可能重叠，合并前按稳定身份去重，不能相加当独立样本。
- 论文历史任务和 IssuePilot 缓存不直接当作今天的开放任务。
- 没发生交互不等于不适合；未合并 PR 不等于低能力。保留 `label_kind` 区分贡献、解决和人工适合度。
- Git 作者与提交者分开，不能把 committer 当成全部代码作者。
- 用户拥有仓库、star 仓库、fork 仓库、实际修改文件分别记录，不能混成一种能力证据。
- 真实数据不足时提交缺口及扩充措施，不用重复行、假行为或演示数据填足规模。

## 7. 跨成员交付契约

以下是 S0 冻结的最小字段要求。D 将它们实现到 `contracts_midterm.py`；字段扩展通过共享变更流程处理。业务示例中禁止包含真实密码或 token。

### 7.1 标识、时间与版本

- 跨模块 `developer_key`、`repository_key`、`file_key`、`file_version_key` 为不透明字符串，其他模块不得解析其中的私有格式。
- A 维护来源 ID 到规范 key 的映射；GitHub numeric ID 可用时优先作为身份依据。仅昵称/邮箱相似不能自动合并，未确认身份保留来源内 key。
- 一个逻辑文件与某个 commit 的文件版本分开标识。改名别名只有在有证据时关联。
- 平台登录 `user_id` 与训练 `developer_key` 分开；D 管理会话身份，A/B 根据可验证 GitHub 身份建立关联。
- C 维护图节点整数索引到规范 key 的双向映射，不能把本次数组行号直接当用户/文件永久 ID。
- 时间统一为 UTC ISO 8601，未知使用 `null`。`event_at`、`observed_at`、`snapshot_at` 各有含义，不互相替代。
- 数据、代码快照、画像、向量、图、划分、模型各自有版本。改变输入内容必须改变对应版本/校验和。

### 7.2 A → B/C：数据快照与编码输入

| 记录 | 必须包含 |
|---|---|
| `DatasetManifest` | `schema_version`、`dataset_version`、`source_versions`、`created_at`、时间覆盖、各实体计数、文件位置/格式/校验和、质量缺口、许可说明 |
| `RepositoryRecord` | `repository_key`、来源仓库 ID、`full_name`、主语言/领域、归档与维护状态、贡献入口、观察时间 |
| `ContributionRecord` | `developer_key`、`repository_key`、`file_key`、`file_version_key`、`commit_sha`、`event_at`、行为类型、作者关联状态、证据位置 |
| `ProjectBehaviorRecord` | `developer_key`、`repository_key`、行为类型、`event_at`/是否未知、`observed_at`、来源 |
| `CodeDocument` | `file_version_key`、`repository_key`、文件路径、`commit_sha`、语言、`content_hash`、内容位置、可用/排除原因 |
| `IssueRecord` | 稳定任务 key、来源 Issue ID/编号、仓库、文本位置、标签、时间、当前可用性与核查时间；解决者/最终 PR 明确属于结果字段 |
| `IssueFileLink` | Issue key、file key、证据种类、`available_at`、置信度、来源；区分事前路径线索与事后解决 PR |

约束：一条入选训练边必须能追溯到来源；不能确认发生时间的兴趣行为不能伪造创建时间。代码不必内联塞进每条记录，交付可定位且校验过的内容即可。

### 7.3 B → C/D：画像和增强特征

| 产物 | 约定 |
|---|---|
| 现有 `DeveloperProfileV2` | 保持已有服务字段兼容；技能名 casefold、等级范围、环境与偏好含义不变 |
| `ProfileEvidence` | 规范 key、技能/经历、证据类型、来源位置、贡献时间、观察时间、置信度、是否用户确认/锁定 |
| `AssessmentSubmission` | `questionnaire_version`、题目 ID/版本、回答、提交时间；用户身份由 D 从 session 注入 |
| `ProfilePreview` | 当前画像、建议变化、依据、冲突/未知、置信度、可接受/拒绝项；预览不等于已保存 |
| `EnhancedProfileFeatures` | `profile_key`、可选 `developer_key`、`profile_version`、`as_of`、`feature_schema_version`、有序 `feature_names`、同长数值 `values`、同长 `observed_mask`、当前兴趣和证据引用 |

`observed_mask=false` 表示未知，不能当低能力零分。B 明确回答、自评、真实证据如何融合，并允许用户修改。C 只消费冻结特征，不在训练脚本里重写问卷评分。

历史实验中的画像只能由预测时点之前的证据生成；今天收集的自评/兴趣不能倒填成几年前已知的训练特征。无历史问答时，C 必须说明代理特征设定；“加入真实问答的效果”另以本期用户—任务评价验证，不能虚构历史问答收益。

### 7.4 C → B：编码服务的离线接口

逻辑接口：

```python
encode_documents(documents, *, encoder_version, output_dir) -> EmbeddingManifest
```

必须输出行到 `file_version_key` 的映射、内容哈希、模型标识/修订版本、tokenizer/分段/池化策略、维度、dtype、成功与失败条数、缓存路径和 SHA-256。不能只有一个无法对齐文件的向量矩阵。

同一缓存键至少包括内容哈希、encoder 修订版本和分段/池化配置。B 如需由语义生成技能建议，使用自己定义的校准规则，并记录这是推断；不能把向量直接称为能力等级。

### 7.5 C → D：模型加载与推荐

逻辑接口（D 在 S0 固定实际签名）：

```python
load_ranker(model_manifest_path) -> Ranker

Ranker.rank_files(context, candidates, *, limit) -> FileRankingBatch

recommend_with_model(
    *, profile, enhanced_features, candidates, model_variant, limit
) -> ModelRecommendationBatch
```

- 模型输入输出由公共契约定义，不返回 PyTorch Tensor 给 HTTP 层。
- `FileRankingBatch` 至少包含用户/上下文、模型/图版本、文件 key、原始分数、排名、覆盖率和无法预测原因。
- `ModelRecommendationBatch` 保持已有 Issue 列表的必要字段，批次增加 `model_variant`、`model_version`、`dataset_version`、`feature_versions`、`mapping_version`、`model_status`、`warnings`。
- 原始内积分数可能无界。C 保留 `raw_score`，为兼容界面采用的任何单调转换必须固定并声明，不能称为完成概率。
- 解释显示可核查的文件、经历、兴趣和约束证据；没有做归因计算时，不伪造某特征对神经模型的精确贡献。沿用 `score_delta` 时，非加法解释使用 0 并明确含义。
- C 提出新增原因码（例如语义/贡献证据），D 更新公共枚举和 OpenAPI；禁止返回前端无法识别的临时字符串。
- 新手/进阶共用模型主干与映射约定，资格/难度等业务约束显式版本化。
- 模型训练、下载权重、全仓采集、全量编码不得在推荐 HTTP 请求中执行。D 加载已经登记的模型，记录失败，不静默换模型。

固定模型变体：

```text
coder_original      # 原版 baseline
coder_profile       # 仅新增增强画像
coder_recent        # 仅新增近期行为/当前意图
coder_combined      # 两项优化
rule_legacy         # 既有规则，仅明确选择的兼容/诊断模式
```

不要把代码中的旧 `MATCH_VERSION_V3` 直接改名为 CODER。真实模型版本由权重、配置和输入模式共同确定。

### 7.6 A/C → D：项目推荐与任务映射

- 既有 `RecommendationItemV3` 是 Issue 结构，不把项目卡片伪装成 `issue_number=0` 的 Issue。
- 新增独立 `ProjectRecommendationItem`，至少包含 repository key、仓库名/URL、排序分、依据、贡献入口、相关模块、关联 Issue、核查时间与状态。
- A 提供项目元数据和入口，C 负责从文件/项目模型结果聚合排序，D 负责路由和展示。
- 文件到 Issue、文件到项目的聚合方式由 C 实现并版本化；原版/优化版正式对比共用同一方式。
- 没有可靠关联时返回缺失/覆盖率，不利用未来解决 PR 伪造当前关联，也不暗中退回规则排序。

## 10. 成员 C：原版 CODER、优化、模型服务与实验

### C1. 第一个里程碑：复现可行性核查

第一周前两天提交可行性消息：官方代码/数据有哪些、缺哪些、准备如何按论文补齐、依赖与硬件实测、首次训练的范围和预计瓶颈。

核查失败时明确阻塞并继续进行独立的编码、图接口、测试与实验准备；不能用旧规则或只有 CodeBERT 相似度的模型替代原版并宣布 baseline 完成。

### C2. 原版 baseline

- 对照论文实现/恢复 CodeBERT 编码、代码与贡献者融合、结构聚合、行为聚合、预测和优化目标。
- 原版与优化代码共享必要工具，但新增画像和时间特征在 baseline 中显式关闭。
- 数据集、CodeBERT checkpoint、结构图、分段、超参数和随机种子可追踪。
- baseline 有独立权重和配置，不能在后来实验中覆盖。
- 若官方 benchmark 可获得，先按原协议复现并记录原协议的时间/快照限制；自建数据使用单独命名的协议，不能把协议变化也算成优化收益。

### C3. 两项优化

1. **增强画像**：消费 B 的结构化经验、能力证据、回答和当前偏好。先确定一个清晰的融合位置，再用验证集选择配置。
2. **近期行为/当前意图**：区分长期经验和近期行为；新增时序特征只能使用预测时点之前的信息。时间权重的参数由验证集确定。

画像和时序特征的交叉部分必须分清：`coder_profile` 只用定义好的画像组，`coder_recent` 只用定义好的近期/意图组；重复字段不能在两个模块里换名后宣称两个独立贡献。

### C4. 训练与推理产物

一个可加载模型包至少包括：

```text
model_manifest.json
weights.<实际格式>
config.json
feature_schema.json
node_mapping.<实际格式>
environment.lock 或等价的精确环境说明
```

manifest 记录模型变体/版本、复现级别、代码提交、数据/划分/图/画像/向量版本、checkpoint、训练参数/种子、权重校验和、输入输出模式、分数转换和已知限制。各文件实际名称由 C 固定在 manifest 中，不依赖别人猜目录。

### C5. 公平评估

- A/B/C/D 四个变体共用划分、候选、负样本/全量排序协议及映射。
- 所有特征、结构、作者行为和代码快照做时间审计；不能只切标签时间。
- 训练、验证、测试边严格区分。已知文件可跨时间出现，但不能把未来交互、结果或代码内容泄漏进训练输入。
- 用验证集调参和早停，测试集只用于冻结后的正式评估。
- 文件推荐报告 Recall@K、NDCG@K、MRR@K；固定 K=5/10/20，明确全量或采样候选及候选数。
- Issue 推荐另外报告用户—任务适合度、可用性、覆盖率和误匹配，不能拿文件 MRR 直接当 Issue 完成率。
- 零历史用户单独报告。原版不支持的用户记录无法预测与覆盖率，不伪造用户节点；优化的冷启动收益单独评价。
- 资源允许时至少 3 个种子；否则写明只完成单种子，不能填虚假的均值/波动。
- 保存逐用户/逐任务预测、指标、耗时与资源测量；提升同时给绝对差和相对差，baseline 为 0 时不计算相对百分比。
- 新版没有提升时如实输出，不能改测试集或只选有利样本。

### C6. 必须交付的产物

|---|---|---|

### C7. 验收

- 原版和至少一个优化变体能在相同协议上训练、保存、重新加载并评估。

- D 能用独立进程加载交付包、调用推理并获得确定结构，模型不需要临时下载。

- 各项优化可独立关闭，能完成 baseline、单项优化、组合优化对比。
- 模型输出不伪装成成功概率，解释不伪造神经网络归因。

| `POST /api/v1/me/profile/import-github`（已有） | 创建/触发贡献证据导入 | B 编排，A 采集 |
| `GET /api/v1/me/profile/import-jobs/{job_id}` | 查询本人后台导入状态 | B 业务状态，D 网关 |
| `GET /api/v1/recommendation-runs/{run_id}` | 查询有权限查看的推荐说明/版本 | C |

规则：

- 所有受保护接口的用户身份来自 session，不接受前端指定任意 `user_id` 或 `developer_key` 切换身份。
- 预览确认检查原画像版本，过期冲突返回 409。后台导入返回作业标识，不让 HTTP 等待全仓处理。
- OAuth、session、错误格式和限流由 D 统一维护，不新建第二套认证。
- 错误沿用现有格式；模型不可用/版本不匹配返回明确状态和 503，不静默用规则顶替。
- D 维护 `docs/openapi_v0.6.yaml` 作为本轮拟议增量版本，保留旧 OpenAPI 文件；API 路径仍使用 `/api/v1`。版本号是计划约定，实际实现时一次性对齐运行配置。
- 普通产品用户不获得任意模型文件路径或训练参数选择权；实验变体由服务端配置/受控开发入口选择。

### D4. 验收

- 干净环境可以初始化独立库、导入小 fixture、启动网页并完成完整流程。

## 13. 合并、测试与冻结

### 13.1 合并顺序

1. D：S0 公共契约、独立数据库配置和最小存储接入。
2. A/B/C：各自目录骨架、契约测试、小 fixture，可独立合并。
3. A：标准数据/代码快照与 011；B：画像业务与 012；C：编码/图/原版模型接口与 013。数据库迁移按号执行，不按 PR 先后乱序。
4. D：业务接线、页面消费真实接口；此时明确原版模型可用范围。
5. B/C：增强画像、优化模型与正式实验；A 按冻结规则更新来源。
6. D：全部集成回归与演示冻结。

迁移作者与 D 共同核对 schema；其他成员的普通业务实现不要求四人同时审阅。一个 PR 尽量只交付一个可验收单元，不把所有成果堆到答辩前一次提交。

### 13.2 训练环境与 CI

- A/B/D 的普通测试和 API 契约不依赖真实外网或 GPU。
- C 将重型训练依赖做为可选环境，提供精确版本/环境锁；D 统一写入公共依赖配置，不能让启动普通网页时强制下载模型。
- 标准 CI 使用小 fixture 做 schema、关键算法、身份和错误行为测试；真实大训练运行单独记录环境、命令、时间和退出状态。
- 当前已有 Python/Node 测试入口以仓库实际命令为准。新增测试目录的 discovery 由 D 显式登记，避免“测试文件存在但从未被 CI 运行”。
- 每人交付需同时说明新增测试、相关既有测试，以及未执行/失败项目；不能只写“全部通过”。

### 13.3 正式实验冻结

由 C 提交一个实验协议 manifest，A/B/D 确认输入含义，至少固定：

```text
dataset_version / code_snapshot_version
split_version / graph_version / candidate_version
train_cutoff / validation_cutoff / test_window
profile_feature_schema / historical_feature_policy
encoder_version / tokenization_pooling_config
negative_sampling_or_full_ranking_protocol
issue_file_mapping_version / project_aggregation_version
shared_eligibility_policy
variant_configs / tuning_budget / seeds / metrics
```

老师数据库后续恢复时，新增数据先形成新版本，完成质量与时间审计再用于新实验；不能替换旧测试输入后保留旧结果名称。正式对比不允许某个变体使用更多可用时间、不同负样本或不同映射。

### 13.4 模型效果和产品行为分别验收

- 离线核心比较：尽量复现原版任务与相同输入条件，先比较模型本身。
- 产品比较：统一状态过滤、Issue/项目映射、设备约束与展示策略，再比较最终推荐。
- 若优化改变了候选范围，额外报告范围、覆盖率和共同候选上的结果，不仅报告变化后的指标。
- 人工适合度评价记录画像、候选和时间，不让标注员看到模型名称/排名后再判断是否合适。
- 问答、近期兴趣、神经模型解释和成长价值都不得使用事后结局作为当时已知特征。

## 14. 最终验收、风险与取舍

### 14.1 中期必须完成清单

- [ ] 五项任务各有明确代码、产物、负责人和实测状态。
- [ ] 独立数据库、论文数据导入、真实贡献/文件关联可用，来源可追溯。
- [ ] 老师库不可用时系统仍可运行；适配器如仅 mock 明确标记。
- [ ] 原版 CODER baseline 已完成关键模块、训练、加载和评估；复现差异透明。
- [ ] 至少一个真正新增优化模块及对应消融完成。
- [ ] 原版和优化版在相同正式协议上有可复现比较，不预设必须正提升。
- [ ] 问答、自评、GitHub 证据生成可确认、可编辑、有版本的画像。
- [ ] 实际贡献代码被正确归属，不能将整仓代码视作本人能力。
- [ ] 首页直接展示推荐；个人信息、详情和推荐说明分开。
- [ ] 文件/Issue/项目推荐对象清晰；真实模型标识与候选状态可查。
- [ ] 多用户隔离、模型不可用、无历史、缺证据和过期状态有处理。
- [ ] 全流程演示、干净环境启动、产物校验与关键复现命令通过。

### 14.2 风险与处理

| 风险 | 负责人 | 处理方式 |
|---|---|---|
| CODER 原代码/处理数据不完整 | C，A 配合 | W1 前两天公开差异清单；先按论文完成小规模关键链路，不挂名替代 |
| 数据大但不能关联到文件/作者 | A | 优先提高有效交互覆盖率，先跑可追溯仓库，再扩大规模 |
| GPU/磁盘/编码成本超出资源 | C | 先测峰值，缓存语义表示、缩小试验图，记录采样策略，不减少 baseline 核心模块冒充完整复现 |
| 老师库长期无法使用 | A | 继续论文和 GitHub 路线；适配接口保持独立 |
| 问答特征没有历史标签支撑 | B/C | 历史代理特征与本期真实问答分开评价，不能编造历史回答 |
| 优化没有提升 | C | 检查特征质量、时间泄漏、融合与调参；如实交付结果和分析 |
| 前端先做完但模型未接入 | D/C | fixture 与真实模型标识分开，W2 必须进行真实加载联调 |
| 集成时多人改同一文件 | D | 唯一编辑者、按队列合并、对冲突逐项核对，不采用整文件覆盖 |

### 14.3 时间不足时怎么缩减

必须保留：原版 CODER、至少一个完整优化、固定数据/协议、真实对比和五项任务基本闭环。

可以后移：第二优化模块的大规模调参、全语言/全仓覆盖、复杂自动导学文档、协作者身份相关拓展、数据库后端迁移。数据规模目标若未达到，报告实际量和原因；不得以造数补足。

不能缩减为：只有页面、只有模型名字、只有语义相似度、只有 mock、没有原版结果、没有共同测试协议。
