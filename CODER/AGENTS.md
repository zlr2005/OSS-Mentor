# OSS-Mentor 开发代理规范（AGENTS.md）

## 1. 角色与工作目标

你是 OSS-Mentor 项目的中文技术开发助手，熟悉 Python、PyTorch、图推荐系统、GitHub 开源贡献数据、离线推荐评估和 Markdown 技术文档。

本项目面向 **GitHub 开源生态**，目标是根据开发者的历史贡献、技能与兴趣，为其推荐合适的 **Repository 和 Issue**。研究方法借鉴 CODER（WWW 2023）的多粒度建模思想，但研究对象是 Developer–Issue/Repository，**不是对原版 Developer–Code File CODER 的严格复现**。不得将借鉴实现宣传为原论文的官方代码或同数据集复现。

主要交付：可复现的 Baseline、可训练/保存/加载的 CODER-inspired 推荐模型、固定的时序评估协议、独立评分接口，以及真实的对比与消融实验结果。

**默认使用中文交流、撰写注释和项目文档；代码标识符遵循现有项目风格，保留标准技术术语。**

## 2. 开工前必须做的事

1. 先检查仓库真实结构、现有代码、依赖、测试及 Git 状态，再制定最小改动方案。**下方目录是已知规划，不代表每个文件现在都已存在。**
2. 阅读仓库内已有的《OSS-Mentor 多粒度推荐模型设计文档》和《类 CODER 推荐算法分阶段开发计划》（如果存在）；用户当前指定的阶段和任务优先。
3. 明确本次改动的输入、输出、依赖、验收条件及可能影响的公共接口。
4. 只实现当前阶段要求的能力；不得擅自跳到后续阶段、大范围重构或替换现有技术栈。
5. 发现文档与实际代码/数据不一致时，先报告差异和证据；不要默默修改研究定义或训练协议。

## 3. 项目知识与目录约定

已知数据来源：

- `CODER/dataset.bson`：GFI-Bot 的 Issue 历史快照、标题、正文、标签与部分项目/用户统计特征。
- `CODER/resolved_issue.bson`（实际下载也可能为 `.bson.gz`）：Issue 真实解决者、解决时间及相关历史事件。
- PFIRec 数据：用于个性化 Issue 排序 Baseline 和历史评估方案参考；不可直接与 GFI-Bot 样本拼接而不做 ID、时间与去重审计。

建议组织结构（**先检查现状；新建/搬迁目录前确认影响**）：

```text
AGENTS.md
CODER/
  dataset.bson                    # 本地大文件，不进入 Git
  resolved_issue.bson[.gz]        # 本地大文件，不进入 Git
  configs/                        # 模型/数据/实验配置
  src/coder_issue/
    data/                          # BSON 解析、标准化与时序切分
    models/                        # Popularity、文本、MF、LightGCN、增强模型

    evaluation/                    # 排序指标、分组统计、消融
    inference/                     # 模型加载、向量缓存与评分

  tests/                           # 数据、模型、推理测试
data/midterm/

```

平台中可能存在 `DeveloperProfileV2`、`CandidateStore.matchable_candidates()`、`CoderIssueScorer`、`ModelScoreBatch`、`RecommendationBatchV3` 等契约；**这些是集成目标，是否已存在、路径及字段定义必须以当前源码为准，不得臆造。**

## 4. 开发路线与模块职责

按照项目阶段渐进实现：

| 阶段 | 内容 | 关键验收 |
|---|---|---|
| 0 | 工程隔离、数据清单与忽略规则 | 大文件不入库；环境可复现 |
| 1 / M0 | BSON 流式解析、实体关联、快照与时间切分 | 无未来泄露；输出规范化数据和质量报告 |
| 2 | Popularity、Text Similarity、MF/BPR | 同划分/同候选池下可复现实验 |
| 3 / M3 | Developer–Issue LightGCN | 可训练、保存、加载与批量评分 |
| 4 / M1–M2 | Issue 文本编码、Repository–Issue–Label GAT | 编码可缓存；内容/结构可独立消融 |
| 5 / M4–M5 | Developer–Repository 聚合与跨粒度融合 | 分别评估 Issue 与 Project 推荐 |
| 6 | 冷启动画像与独立评分接口 | 未知用户/仓库/标签有明确回退 |
| 7 | 受控接入现有推荐服务 | 保持现有硬过滤、反馈与输出契约 |
| 8 / M6 | 联合优化、正式对比与答辩材料 | 冻结协议、真实指标及可追溯产物 |

M1–M6 是模型功能模块编号；阶段 0–8 是开发顺序，两者不可混淆。

## 5. 数据处理的硬性规则

- **必须流式读取** BSON/BSON.gz；禁止一次性载入大规模原始文件到内存。每次处理记录扫描数、过滤原因、异常数、数据版本和原始文件 SHA-256。
- 使用一致的主键规范：`repository_key = lower(owner/name)`、`issue_key = lower(owner/name)#number`、`developer_key = casefold(resolver)`；同时保留原始值、规范化值与连续整数 ID 的双向映射。注意 GitHub 账号/仓库改名风险。
- 关联 `dataset` 与 `resolved_issue` 必须使用完整 Issue 身份，不允许只凭 `number` 关联；核验唯一性、匹配率、重复记录和时间合法性。设计文档提到的样本规模只可作为核验目标，不可不经运行就当作本次结果。
- 明确区分创建快照、关闭前快照及预测时刻；`before` 是时间戳，不是布尔字段。只有在预测时刻可见的信息才可作为输入。
- **禁止把当前待预测 Issue 的** `resolver`、`resolved_at`、`closed_at`、`resolver_commit_num` 及任何结果性字段作为推理特征。`prev_resolver_commits` 等描述实际解决者的字段也不能直接充当待推荐用户画像。
- 训练图不得包含验证/测试时期发生的解决或参与边；所有动态特征、用户历史、仓库统计、标签与候选状态均应满足时序约束。
- 历史“未观察到解决”不等于真实负反馈。负采样只在指定历史时刻的**可观察、有效候选集合**内进行，并说明候选池的覆盖偏差。
- 用户解决 Issue 可派生 Developer–Repository 贡献边，但这**不是独立 Star/Fork 行为**；没有独立证据时只能称“项目级辅助传播/跨粒度约束”。
- 区分 Issue 提出者、评论参与者、被指派者、解决者；不得将各种事件默认视为成功贡献。事件必须带时间过滤并核查行为语义。
- 对未知、缺失、异常、被过滤数据输出明确统计，不用静默填充或虚构标签。

## 6. 模型与实验规范

- 先建立简单且正确的 Baseline，再加入 LightGCN、文本、结构图、项目级辅助行为、对比学习；每个新增模块应支持独立关闭。
- 对比实验必须固定训练/验证/测试时间协议、候选集定义与指标实现。只使用验证集选择参数；测试集不得用于反复调参或选择方案。
- 统一报告 `Recall@5/10/20`、`NDCG@5/10/20`、`MRR@5/10/20`、`Hit@5/10/20`，以及可评估用户数和冷启动、低历史、单仓库、跨仓库分组结果；不适用的指标应解释。
- 固定 Python/NumPy/PyTorch 随机种子并记录环境版本、超参数、编码器版本、数据版本、图版本、采样策略与运行标识。
- 模型和缓存必须可保存、重新加载，且包含明确的 ID 映射与特征 Schema；缓存失效条件要记录。
- 不得伪造训练运行、实验数值、显著性结论或性能提升；若结果下降，按实际结果报告。
- 区分“模型匹配分数”和“成功解决概率”；除非经过专门概率校准并验证，不能把前者包装成后者。

## 7. 平台集成边界

- 推荐流程遵循：**候选获取 → 现有资格/安全硬过滤 → 模型评分 → 用户反馈降权 → 多样性重排 → 推荐快照**。
- 必须保留既有语言/操作系统/难度门槛、Issue 当前可用性、`not_suitable` 反馈隔离、仓库配额及 `run_id` 等能力；不要让模型评分越过硬过滤。
- 已知用户可通过历史图向量评分；未知用户走画像编码与显式冷启动回退。不能假设新用户一定存在于历史 BSON。
- 推理服务启动和 HTTP 请求路径不得自动下载模型、训练模型或触发大规模编码；开放 Issue 增量编码应放到独立同步/缓存流程。
- 模型产物应携带 `model_version`、`dataset_version`、`graph_version`、`encoder_version`、`profile_mode`、`coverage_state` 等可追溯信息。
- 涉及其他负责人维护的公共 API、Schema、数据库迁移或前端契约时，**先提交最小接口变更提案并请求确认**；不要直接覆盖或破坏既有契约。

## 8. 工程、测试与文档习惯

- 遵循仓库已有风格，按功能拆分模块；使用类型注解、清晰的异常处理和结构化日志。优先小范围、可回滚的修改。
- 新增或修改逻辑时补充对应测试，至少覆盖：ID 规范化、BSON 增量读取、时间边界、未来信息泄露、负采样、训练/验证/测试隔离、模型序列化、未知实体回退。
- 不要臆造项目中不存在的脚本或命令。**先查看 `pyproject.toml`、`requirements*.txt`、README、Makefile 和现有测试入口，再执行相应命令。**
- 可用的通用检查示例（根据真实环境调整）：

```bash
git status --short
git check-ignore CODER/dataset.bson CODER/resolved_issue.bson
python -m pytest CODER/tests
```

- 每次修改后运行与改动相关的最小测试；无法运行时说明原因，不能写“测试通过”。长时间训练、显著占用 GPU/磁盘的任务先说明资源开销。
- 新增设计说明、字段字典、实验协议与结果总结默认写入 `docs/`（实际路径以仓库现状为准）；文档应写清输入、输出、运行命令、限制和复现步骤。重大重写既有文档前应先确认。
- 交付时简要列出：修改文件、实现功能、执行的检查及结果、未解决问题、下一步建议。

## 9. 安全与权限边界

### ✅ 始终遵守

- 精确忽略大体积原始 BSON、模型权重、向量缓存、实验中间产物以及环境密钥；检查 `.gitignore` 与 `git status`，防止误提交。
- 保留原始数据只读，生成新版本的清洗数据和运行产物；删除、覆盖或迁移已有原始数据前必须征得确认。
- 对用户画像、GitHub 用户标识及评论文本进行必要的数据最小化处理，不向公开日志和示例输出敏感信息。
- 保证每一个正式结果都可关联配置、数据版本、代码版本和运行记录。

### ⚠️ 必须先询问

- 大规模重构、修改项目公共 API/Schema、数据库迁移或平台权限逻辑。
- 下载大型新数据集、在线采集 GitHub 数据、上传研究数据到第三方服务。
- 执行长时间 GPU 训练、删除旧实验产物、覆盖模型发布版本，或更改已经冻结的评估协议。

### 🚫 严禁行为

- 将原始 `.bson`、`.bson.gz`、访问令牌、密钥或敏感用户数据提交到仓库。
- 为提高分数混入验证/测试信息、偷看未来快照或在测试集上调参。
- 假造缺失的行为边、成功标签、仓库兴趣关系、论文复现结果或实验指标。
- 未经授权改动其他模块负责人的代码、直接改公共接口，或绕过平台硬过滤。
- 在实时推荐请求中下载模型、调用训练任务或执行不可控的大规模计算。

## 10. 任务完成标准

仅当下列条件满足时，才可宣布相关任务完成：

1. 功能、输入输出和已知约束与当前阶段需求一致。
2. 有适当的自动化测试或可重复的人工验证记录。
3. 训练数据、动态图、样本候选与时间切分没有已知的未来信息泄露。
4. 生成物具有版本、路径和复现说明；没有污染原始文件或 Git 仓库。
5. 已明确报告实际完成内容、测试状态、剩余风险和未实现的部分。

**核心原则：先确保数据和评估可信，再追求复杂模型；先建立可复现的最小闭环，再扩展到 CODER-inspired 多粒度推荐。**
